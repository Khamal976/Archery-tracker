# Трекинг тренировок по стрельбе из лука

Локальное веб-приложение: на телефоне вносишь попадания прямо на рубеже, на десктопе
разбираешь статистику и сравниваешь настройки снаряжения. Работает офлайн, ставится как PWA.
Бэкенда, аккаунтов, облака, аналитики и сетевых запросов нет — данные лежат только в браузере,
в IndexedDB. Перенос между устройствами — экспортом и импортом файла.

## Запуск

Первый раз — установить зависимости:

```bash
npm install
```

Дальше каждый раз:

```bash
npm run dev
```

Открыть http://localhost:5173. Команды даны по одной: в Windows PowerShell 5.1 склейка
через `&&` не работает — если хочется одной строкой, там это `npm install; npm run dev`.

Остальные команды:

```bash
npm run build
```

```bash
npm test
```

```bash
npm run icons
```

`npm run icons` перерисовывает иконки PWA (`public/icon-*.png`, `favicon.svg`) — они
генерируются кодом, а не лежат бинарниками.

## Установка на Android

Приложение — статика без бэкенда, поэтому «установить» его значит открыть страницу в Chrome
и добавить на домашний экран. Есть одно жёсткое условие: **service worker живёт только в
защищённом контексте** — это `https://` или `localhost`. По локальному IP вида
`http://192.168.1.5:5173` приложение откроется и будет работать, но офлайна и установки
не будет.

### Быстро посмотреть с телефона (без установки и офлайна)

```bash
npm run dev -- --host
```

Vite напечатает адрес в локальной сети — открыть его в Chrome на телефоне. Ноутбук и телефон
должны быть в одной сети; Windows может спросить разрешение брандмауэра.

### Поставить по-настоящему, вариант 1: кабель и ADB

Самый надёжный способ: адрес `localhost` не меняется никогда. Если `adb` ещё нет, поставить
Android SDK Platform-Tools — это ~10 МБ, Android Studio не нужна:

```bash
winget install --id Google.PlatformTools
```

Включить на телефоне отладку по USB, подключить кабель, принять запрос авторизации и:

```bash
adb reverse tcp:4173 tcp:4173
```

Дальше `npm run build`, `npm run preview -- --port 4173`, и на телефоне открыть
`http://localhost:4173`. Для Chrome это защищённый контекст, поэтому появится пункт меню
«Установить приложение». После установки всё лежит в кэше и работает без компьютера и без
сети. Кабель нужен снова только чтобы обновить версию.

### Вариант 2: без кабеля, через флаг Chrome

Ставить нечего, но приложение окажется привязано к адресу ноутбука в локальной сети.

Собрать и поднять раздачу по сети:

```bash
npm run build
```

```bash
npm run preview -- --host --port 4173
```

На телефоне открыть `chrome://flags/#unsafely-treat-insecure-origin-as-secure`, вписать туда
адрес вида `http://192.168.1.5:4173`, включить, перезапустить Chrome. Теперь этот адрес для
Chrome защищённый: service worker зарегистрируется, появится «Установить приложение».

Подвох: origin установленного приложения — это тот самый `IP:порт`. Если роутер выдаст
ноутбуку другой адрес, установленное приложение будет открываться из кэша, но перестанет
обновляться. Лечится статическим адресом в настройках роутера или переходом на вариант 1.

### Вариант 3: GitHub Pages (используется сейчас)

Приложение выкладывается на GitHub Pages автоматически: в репозитории лежит workflow
[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml), который на каждый push в
`main` ставит зависимости, прогоняет тесты, собирает и публикует. Автономность от этого
не страдает: после установки приложение не делает ни одного сетевого запроса, данные
остаются в браузере телефона.

Обновить приложение на телефоне:

```bash
git push
```

Базовый путь workflow вычисляет сам: репозиторий `username.github.io` отдаётся из корня,
любой другой — из подпапки `/имя-репозитория/`, и сборка идёт с соответствующим `BASE_PATH`.
Тесты в CI не декоративные: если математика счёта или мержа сломается, выкладка не пройдёт.

Разовая настройка после создания репозитория: **Settings → Pages → Source: GitHub Actions**.

На бесплатном тарифе сайт публичный. Приватный Pages требует платного плана — если это
важно, подойдёт любой другой хостинг статики с HTTPS: Netlify, Cloudflare Pages, Vercel.

Если хостинг отдаёт приложение из подпапки (типичный случай GitHub Pages), собирать нужно
с указанием базового пути, иначе не найдутся ни ассеты, ни service worker:

```bash
$env:BASE_PATH='/имя-репозитория/'; npm run build
```

### После установки

Chrome на Android обычно молча выдаёт постоянное хранилище установленному приложению —
статус видно в настройках приложения внизу. Вибро таймера работает, экран не гаснет во время
сессии. Обновление приложения прилетает само при следующем запуске с сетью: service worker
собран в режиме `autoUpdate`.

## Модель данных

```
сессия → этапы → серии → выстрелы
```

- **Сессия** — одна тренировка или один раунд. Ссылается на формат, место, заметку перед
  стартом, разбор после и на **конкретную версию сетапа**, а не на сетап целиком.
  Завершить можно любую сессию в любой момент — статистика сохранится, а недобитый
  стандартный формат просто не пойдёт в рекорды.
- **Этап** — дистанция + фейс + число серий + стрел в серии. Простые форматы (WA 18 м,
  WA 70 м) — один этап; FITA 900 и FITA 1440 — несколько этапов с разными дистанциями.
- **Серия** — один подход. У серии свой режим ввода: по мишени или числами.
- **Выстрел** — координаты в миллиметрах, индекс спота, номинал, флаги X, промаха и
  повторного спота.

Все mrad-метрики считаются по дистанции своего этапа. Идентификаторы — UUID, у каждой
сущности есть `updatedAt`; удаление мягкое (`deletedAt`), тумбстоуны едут в бэкапе, иначе
удалённая на одном устройстве сессия воскресала бы при импорте с другого.

## Конвенция координат

**+x вправо, +y вверх, с точки зрения стрелка, смотрящего на мишень.** Единица — миллиметр.
Начало координат — центр фейса, а для многоспотовых фейсов — **центр своего спота**
(поэтому споты складываются в одну группу и кучность считается корректно).

Конвенция одна и та же в хранении, метриках, CSV и подсказке по прицелу. SVG рисует y вниз;
перевод живёт ровно в одном месте — `src/core/viewbox.ts`.

Диаметр стрелы при определении кольца не учитывается: точка тапа — это точка. Попадание
точно на линию кольца засчитывается в пользу большего номинала.

## Что где лежит

| Путь | Что там |
| --- | --- |
| `src/core/` | Чистая математика без React и Dexie: фейсы, счёт, метрики, форматы, поля сетапов, справочник по настройке, расчёт спайна |
| `src/db/` | Схема Dexie и операции над данными |
| `src/lib/` | Агрегация статистики, экспорт/импорт, таймер, wake lock |
| `src/ui/` | Мишень в SVG, тепловая карта, блоки метрик, атомы интерфейса |
| `src/screens/` | Экраны |

Тесты лежат рядом с кодом (`*.test.ts`) и покрывают только математику — граничные случаи
счёта, метрики, мерж бэкапа.

## Принятые решения по формулам

Эти вещи в ТЗ были заданы не до конца; выбор зафиксирован здесь, чтобы результаты были
воспроизводимы.

- **Порог данных.** Метрики кучности считаются от n ≥ 3 выстрелов с координатами. Меньше —
  пометка «мало данных», нулей не подставляем. Серии, введённые числами, координат не имеют
  и в кучность не идут вовсе.
- **CEP** — эмпирический перцентиль расстояний от центроида с линейной интерполяцией
  (тип 7, как в numpy и Excel `PERCENTILE`). Рэлеевская оценка не реализована сознательно:
  она предполагает круговую нормальность и врёт на вытянутых группах. При n < 10 CEP95
  подписывается «ориентировочно»; на трёх точках он почти упирается в максимум.
- **Флаер** — выстрел дальше 2.5 радиальных СКО от центроида, где центроид и СКО считаются
  **по остальным выстрелам**. Без этого одинокий далёкий выстрел раздувает СКО настолько, что
  сам под порог не попадает, и на серии из шести стрел правило не срабатывает никогда.
  Проход один, итеративного пересчёта нет. Флаеры ищутся по этапу целиком (n меньше пяти —
  пометок нет), чтобы на разных уровнях статистики они не противоречили друг другу.
  Исключение флаеров меняет только кучность и смещение — счёт, средний балл и рекорды
  не трогает никогда.
- **Значимость смещения** для подсказки по прицелу — по каждой оси независимо:
  |среднее| > 2 · СКО / √n. Поэтому подсказка бывает только по вертикали. Прицел двигается
  **вслед за группой**.
- **Сессия целиком** при нескольких этапах считается в mrad: точки переводятся по дистанции
  своего этапа. Миллиметры между дистанциями не смешиваются — на многоэтапной сессии их
  просто нет.
- **Спот-зона.** Тап дальше радиуса зоны спота — промах. Между внешним кольцом и краем зоны
  тоже промах, но с координатами: он участвует в кучности, а не выпадает из неё.
- **Внутренняя десятка.** На фейсе с флагом «только внутренняя десятка» внешняя десятка даёт
  9, внутренняя — 10 и увеличивает счётчик X (X — тай-брейк в рекордах).
- **Полнота сессии.** Этапы без ограничения по сериям неполноты не создают. В личные рекорды
  идут только завершённые полные сессии стандартных форматов.
- **Отстрел без счёта** не участвует в среднем балле — ни в графике по сессиям, ни в сравнении
  сетапов, ни в рекордах: баллов там нет, и нулём их подменять нельзя. В кучность, тепловую
  карту и объём тренировок он входит полностью.
- **Часы объёма** — сумма активного времени сессии; пауза не считается. Время копится, пока
  открыт экран ввода.
- **Мерж импорта** — last-write-wins по `updatedAt`; при равенстве остаётся локальная запись,
  поэтому повторный импорт одного и того же файла ничего не меняет.

## Подбор стрелы (динамический спайн)

Экран `#/spine`. Формулы и справочники взяты из **Stu Miller's Dynamic Spine Calculator**,
версия **V3 (Rev 5-12, май 2012)** — [страница автора](https://heilakka.com/stumiller/).
Официальный сайт отдаёт только V2 (Rev 12-25-10, обновление от 14.02.2011); V3 расходилась
по форумам напрямую от автора и содержит базу втрое больше. Ничего новее с тех пор не выходило.

- **Что откуда.** `scripts/extract-spine-db.py` вытаскивает справочники из исходного `.xls`
  в `src/core/spineData.ts` (474 древка, 275 луков, 20 тетив, 26 пород дерева, 90 хвостовиков,
  91 строка таблицы полки). `scripts/fetch-skylon-db.py` добирает 153 древка Skylon с сайта
  производителя в `src/core/spineDataSkylon.ts` — этой марки в базе 2012 года нет вовсе.
  `scripts/fetch-retail-db.py` берёт ещё 416 древков 82 серий шести марок (Easton, Gold Tip,
  Victory, Carbon Express, Black Eagle, Nexxus) с карточек Lancaster Archery
  в `src/core/spineDataRetail.ts`. Все три списка складываются в `src/core/shafts.ts` —
  1025 древков, у каждой записи проставлен источник, он же виден в интерфейсе.
  Скрипты разовые, результат закоммичен; при сборке не запускаются. Сгенерированные файлы
  правкам не подлежат — менять надо скрипт.
- **Как читается карточка ритейлера.** Заводская таблица напечатана в трёх видах:
  списком через `|` с шапкой `Spine | GPI | OD | Length`, той же строкой
  `340 (9.5 gpi) .267"` и вариантом `250 (8.1 gpi/OD .295") 400 spine`, где торговый
  размер и спайн — разные числа. Смысл колонок берётся **из шапки**, а не из их порядка:
  у алюминиевых серий первая колонка называется `Size` и содержит код трубки (`2712` — это
  27/64″ при стенке 12 тысячных), а прогиб стоит отдельной колонкой `Deflection @ 28”`.
  Где такой таблице нечего дать, кроме кода, модель пропускается. На карточках последних
  лет спецификации нет в разметке вовсе — она лежит HTML-эскейпом в атрибуте виджета
  отзывов; оттуда её тоже читаем, но только у того тега, чей адрес совпадает с канонической
  ссылкой страницы, иначе втянется описание соседнего товара из блока рекомендаций.
- **Кого пропускаем и почему.** Правило прежнее: нужны все три числа — спайн, GPI и наружный
  диаметр. Диаметр входит в расчёт напрямую (`(диаметр − 11/32) × 30`, до 4 фунтов),
  подставить его неоткуда. Из 302 страниц каталога полные строки дают 83, и они
  складываются в 82 серии; ещё 6 — уценка поштучно, не позиция каталога. Остальные 213
  пропущены: 105 печатают спайн и GPI без диаметра, 61 не имеет спецификации вовсе
  (среди них аксессуары вроде правки древков), 37 дают только внутренний диаметр,
  5 — таблицу спайна с весом без колонки диаметра, ещё 5 — алюминиевые коды трубок,
  из которых прогиб не восстановить. Разбор каждой пропущенной страницы с причиной лежит
  в `retail-report.txt`. Сайт Easton напрямую по-прежнему недоступен: отдаёт файлы
  со скоростью около 25 КБ в минуту, каталог за разумное время не выкачивается.
- **Чем проверяется, что разбор не поехал.** Не монотонностью «жёстче спайн — больше GPI
  и диаметр»: на реальных заводских таблицах она не выполняется. У X10 спайн 350 весит
  8.8 гран, а более слабый 380 — 8.9; у X10 Parallel Pro самый слабый 1150 толще, чем 1000,
  потому что это другая трубка того же семейства. Вместо неё — жёсткость самой трубки.
  У тонкостенной трубы жёсткость на изгиб растёт как D³·стенка, а вес на дюйм — как
  D·стенка, поэтому произведение `прогиб × D² × GPI` почти не зависит от модели: по всем
  1025 записям оно лежит внутри 0.10…0.90. Неверно прочитанная колонка промахивается мимо
  коридора в разы и ловится сразу: коды трубок X23, которые ритейлер сам подписал словом
  Spine, дают 2.9…4.2, миллиметры вместо дюймов у Nexxus — 114. Проверка живёт и в скрипте,
  и в `shafts.test.ts`.
- **Сверка с базой Стю.** Два справочника пересекаются по 16 кодам алюминиевых трубок
  (XX75 Platinum Plus и X7 Eclipse против XX75 у Стю): прогиб сходится в пределах 0.016″,
  диаметр — 0.008″, причём Стю пишет номинал в 64-х долях, а ритейлер измеренное значение.
  Gold Tip Series 22 совпал по всем трём числам до знака — 0.300″, 7.3 GPI, .338″. Это
  и есть основание доверять остальным строкам: формат страниц один и тот же.
- **Совпадения ключей между источниками.** При одинаковых «производитель / серия / размер»
  побеждает более свежий источник. Таких пар восемнадцать, и они трёх видов. Gold Tip
  Velocity 300 — то же древко, у которого производитель за годы уточнил вес и диаметр
  на пару сотых. Carbon Express Mach 5 250 — уже другое древко под тем же именем: у Стю
  это старый размерный код со спайном .404, в нынешнем каталоге — спайн .250. Easton
  «X 10» и «X10» — одна серия, записанная по-разному, и цифры разошлись всерьёз: у Стю
  на спайне 380 стоит диаметр .263″, а в заводской таблице .215″, и такой толстой X10
  не бывает. Ключ поэтому сравнивается без пробелов и знаков; во всём справочнике так
  сходится ровно эта пара, а Hunter и Hunter XT остаются разными. Ни одна серия
  не разваливается: у ритейлера есть все размеры старой записи и ещё несколько сверх.
- **Материал — со страницы, а не из названия.** Строку «Construction:» ритейлер печатает
  прямо в спецификации, и она честнее имени: у X10 там «carbon fiber/7075 precision alloy»,
  то есть гибрид, хотя по названию его от карбона не отличить, а у RX-7 — «7178 Aluminum»,
  хотя на металл в имени нет и намёка. Заодно это сходится с базой Стю, где X10 тоже
  записан гибридом. Название остаётся запасным вариантом, если строки нет.
- **Константы не трогаем.** Коэффициенты 2.8, 0.4, 125, 9.5, 0.025 и 30 автор подобрал
  эмпирически по отстрелу на машине. Вывода из физики у них нет, поэтому они перенесены как
  есть: любое «улучшение» разошлось бы с эталоном.
- **Формулы взяты из книги, а не восстановлены по значениям.** Их текст вытащен из `.xls`
  через Excel (`xlrd` отдаёт только значения). Это не педантизм: на исходном сетапе автора
  множитель по GPI равен 1.0097, и под это значение одинаково хорошо ложатся и настоящая
  формула `1 + (11 − GPI)/100`, и ошибочная `1 + 0.28·(GPI − 10)` — они совпадают ровно там.
  Вторая при этом обнуляется на GPI 6.43 и уходит в минус ниже, а таких древков в базе
  самого Стю 98 штук. Ошибка обнаружилась только когда лёгкая таргетная трубка дала
  динамический спайн 10 фунтов вместо 82.
- **Сверка.** `spineReference.test.ts` гоняет расчёт по десяти точкам, посчитанным самим
  Excel: формулы Стю переписаны один в один в отдельную книгу (исходный лист под паролем,
  входы в нём менять нельзя), точки специально разнесены — GPI от 3.6 до 15.5, деревянное
  древко, футинг, бочкообразное древко, персональная поправка обоих знаков. Первая точка
  воспроизводит сетап, сохранённый в исходном файле. `spine.test.ts` добавляет проверки
  направлений и краёв, `shafts.test.ts` — проверки самих справочников.
- **Ступенчатый поиск по таблице полки.** В оригинале это `VLOOKUP` с приблизительным
  совпадением, то есть ступенька, а не интерполяция. Повторено как есть — ради совпадения
  с эталоном, хотя плавная кривая выглядела бы аккуратнее.
- **Допуск лука** берётся из той же таблицы и зависит от положения полки, а не от фунтов:
  лук, прорезанный за центр, прощает более широкий разброс спайнов (±3.04 # при −0.1875″
  против ±0.91 # при +0.25″).
- **Границы применимости.** Модель откалибрована на традиционных луках с пальцевым отпуском
  и на древках 4.8–10.7 мм. Поправка на диаметр линейна (`(диаметр − 11/32) × 30`), поэтому
  на современных таргетных трубках 3.2–4.2 мм она экстраполируется далеко за пределы выборки
  и снимает 3–4 фунта. Экран показывает предупреждение при диаметре меньше 6 мм. Это
  относится ко всей серии Skylon id 3.2 и id 4.2.
- **Бочкообразные древки.** У части моделей (Maxima, Hammerhead, Airforce) сечение
  переменное, передок жёстче. В базе они помечены процентом, который снимается со
  статического спайна и заодно двигает точку баланса. Ненулевой он у 36 древков из 474.
  У записей из карточек ритейлера этот процент нулевой: производители его не печатают,
  а придумать нельзя. На бочкообразных сериях оттуда — X10, X10 ProTour, A/C/E, RX-7,
  Maxima RED — расчёт поэтому показывает древко жёстче, чем оно ведёт себя: поправка Стю
  в 2–5 % стоила бы двух-четырёх фунтов динамического спайна. Молчать об этом нельзя,
  поэтому сама бочкообразность берётся со страницы как признак: производитель называет её
  словами («Barreled design» у X10, «stiffer ends» у Maxima), и по этому слову запись
  помечается флагом `barreled`, а экран подбора выводит предупреждение. Ловится именно
  фраза о трубке: у Victory «Taper Lock» — это вставка, у XX75 Tribute «nock swage» —
  обжим под хвостовик, и обе трубки параллельные. Отсутствие флага не значит «параллельная»,
  оно значит «на странице об этом не сказано».
- **Правки исходника.** Строка «Wood Shaft» выброшена: это не запись справочника, а ячейка
  ручного ввода со значениями последнего расчёта владельца файла. У AC Injexion производитель
  исправлен на Easton, у «Unknown / Generic» — на «Generic / Carbon». Хвостовик
  «Easton 420 UNI Bushing + Super Nock» в исходнике записан дважды с разным весом (24 и 23
  грана) — оставлена первая строка. Производители `Easton_Aluminum`, `Easton_Carbon`
  и `Easton_Hybrid` сведены в «Easton»: материал выбирается отдельным полем, а иначе
  рядом с записями из других источников получается четыре разных Easton в одном списке.
- **Одинаковые числа у разных серий — не ошибка.** У Skylon Brixxon, Novice и Radius это
  физически одна трубка id 4.2, различаются допуском на прямизну и графикой. Схлопывать
  их нельзя: древко ищут по имени, написанному на трубке. Тест проверяет уникальность
  только внутри серии. У ритейлера то же самое: Gold Tip Hunter, Hunter XT и Hunter Pro —
  одна трубка разных допусков, и все три остаются. Схлопывается только одно и то же
  название: комплектация из имени вырезается («w/Half-Outs», «w/HIT Inserts»), а карточки
  вроде «Easton 5mm FMJ» и «Easton FMJ 5mm» сводятся к первому написанию — это буквально
  один товар, у которого в заголовке переставлены слова.

## Мишени

Фейс — это данные: габариты, кольца с радиусами и номиналами, флаг X, флаг «только
внутренняя десятка», геометрия спотов, шаг сетки для пустого поля. Новый фейс заводится из
интерфейса (Настройки → Мишени), правка кода не нужна. Из коробки: WA 122, 80, 60, 40,
трёхспот 40 вертикальный и треугольный, компаунд 40 и компаунд 80 (6 колец), пустые поля
40, 60 и 80 см для blank bale.

Кольца рисуются каноническими цветами WA, но приглушёнными: чистого белого и яркого голубого
в приложении нет нигде — на солнце они слепят.

## Справочник по настройке

Раздел «Настройка лука» (`/tuning`) — личный конспект владельца: центровка плечей, база,
тиллер, насечки на тетиве, посадка хвостовика, центр-шот, планжер и метод отхода. Лежит
данными в [`src/core/tuning.ts`](src/core/tuning.ts), правится там же.

Разделы привязаны к группам полей сетапа: в карточке снаряжения над группой «Плечи» стоят
ссылки на «Центровку плечей» и «Тиллер», над «Тетивой» — на «Базу», «Насечки» и «Посадку
хвостовика», над «Плунжером» — на «Центр-шот» и «Планжер».

Иллюстрации лежат в `public/tuning/` и готовятся из исходного PDF скриптом:

```bash
node scripts/tuning-images.mjs "C:/путь/Настройка рекурсивного лука.pdf"
```

Скрипт вытаскивает JPEG-потоки прямо из PDF, отбирает нужные по `MANIFEST` и ужимает их
до 1000 px и качества 68 — оригиналы весят 3.5 МБ, а всё содержимое уходит в офлайн-кэш.
В `MANIFEST` попали только собственные фотографии и рисунки автора; превью чужих роликов
из документа сознательно не переносятся. Единственная нарисованная кодом схема —
картина попаданий при методе отхода в [`TuningFigures.tsx`](src/ui/TuningFigures.tsx).

## Экран блокировки и батарея

Показать страницу поверх экрана блокировки телефона веб-приложение не может — это флаг
нативной Activity. Поэтому телефон просто не блокируется, пока идёт сессия
(Screen Wake Lock), а картинку гасит собственный дежурный слой: почти чёрный экран с текущим
счётом, тап по нему возвращает ввод без разблокировки. Wake lock снимается на паузе и при
выходе с экрана ввода; в режиме энергосбережения Chrome может отказать — это не ошибка,
состояние сессии всё равно пишется в базу после каждого выстрела.

Вибро таймера работает на Android. На iOS `navigator.vibrate` не поддерживается — там
останутся звук и визуальный отсчёт.

## Обратная связь

Настройки → «Написать об ошибке или идее». Форма записывает заметку в базу и собирает
готовое письмо: тип, текст, где случилось, дата, версия сборки и браузер с размером экрана.
Письмо открывается в почтовом клиенте — приложение ничего никуда не отправляет само,
отправку подтверждает человек. Поэтому и офлайн работает: почтовый клиент положит письмо
в исходящие.

Записи хранятся рядом с тренировками, попадают в бэкап и переезжают между устройствами.
Их можно копить на рубеже, а разбирать потом: закрытые уходят в отдельный список.

Адрес получателя — константа `FEEDBACK_EMAIL` в
[`src/core/feedbackMail.ts`](src/core/feedbackMail.ts), одно место на всё приложение.

## Живучесть данных

При первом запуске приложение просит `navigator.storage.persist()`, чтобы браузер не выселил
IndexedDB. Если последнего экспорта не было дольше 14 дней, на главной появляется
ненавязчивое напоминание про бэкап — без модалок и без блокировки работы. Фактический статус
хранилища виден в настройках.

Полный бэкап — JSON со всеми сессиями, этапами, сериями, выстрелами, сетапами со всеми
версиями, кастомными фейсами и настройками. CSV — плоская таблица выстрелов для Excel
(разделитель `;`, десятичная запятая, BOM), только на выгрузку.
